Agentes y control de hardware

Modo explicador · Referencias 2025–2026

Cómo se le da control de hardware a un agente con tools

Un agente (un LLM dentro de un bucle) no toca el hardware directamente: lo hace a través de tools — funciones con un esquema claro que envuelven el driver o la API del dispositivo. Esta página recorre el patrón completo, con ejemplos de SDR, radar, robótica e instrumentación.

Patrón: tool / function calling + MCP Dominio: SDR, ROS 2, lab, PLC/GPIO Salvaguardas: HITL + HIL

01 La idea central

Un LLM solo produce texto. Para que "mueva" algo físico hay que darle un repertorio de acciones ejecutables y un lazo que las ejecute por él.

El agente no habla con el hardware: habla con tools. Una tool es una función con nombre, descripción en lenguaje natural y un esquema de parámetros (JSON Schema). El modelo elige qué tool llamar y con qué argumentos; un componente externo (el cliente/host del agente, o un servidor MCP) ejecuta esa llamada contra el driver real y le devuelve el resultado.

Esto convierte "controlar hardware" en tres piezas: (1) envolver el dispositivo como tool, (2) cerrar el bucle percibir→decidir→actuar→medir, y (3) acotarlo con salvaguardas antes de que algo se mueva de verdad. El resto de la página es exactamente eso.

Modelo mental

El LLM es el planificador. Las tools son el sistema nervioso motor. El servidor/driver es el músculo. El sensor que devuelve lectura es la propiocepción. Sin esa realimentación, el agente actúa a ciegas.

02 Paso 1 · Exponer el dispositivo como tool

Function calling define el "qué puedo hacer"; MCP estandariza el "cómo se conecta" para no reescribir una integración por cada dispositivo.

La definición de una tool

Toda tool se declara con name, description y un inputSchema en JSON Schema que lista los parámetros, sus tipos y cuáles son obligatorios. El modelo usa la descripción y el esquema para decidir la llamada; la claridad del esquema es decisiva para que acierte. Esquema de una tool que ajusta un SDR tipo USRP:

{
  "name": "sdr_set_rx",
  "description": "Configura el receptor del USRP: frecuencia central, tasa de muestreo y ganancia.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "center_freq_hz": {"type":"number", "minimum":70e6, "maximum":6e9},
      "sample_rate_sps": {"type":"number", "maximum":56e6},
      "gain_db": {"type":"number", "minimum":0, "maximum":76}
    },
    "required": ["center_freq_hz", "sample_rate_sps"]
  }
}

Fíjate que los límites físicos del dispositivo ya viven en el esquema (minimum/maximum). Es la primera línea de defensa: el modelo ve el rango válido, y el servidor rechaza lo que se salga de él. Los rangos del ejemplo corresponden al orden de magnitud de un USRP (sintonía de decenas de MHz a varios GHz, ganancia de RX hasta ~76 dB); consulta la hoja del equipo concreto antes de fijarlos.

MCP: el conector estándar

El Model Context Protocol (MCP) estandariza esa capa con una arquitectura cliente–servidor sobre JSON-RPC. El cliente pide el catálogo con tools/list, el modelo elige, y el cliente ejecuta con tools/call; la respuesta vuelve en un campo content estructurado, con isError para fallos. Un servidor MCP no es más que un proceso que envuelve tu driver o la API del dispositivo y publica esas tools. Así, el mismo SDR —o robot, o instrumento— queda disponible para cualquier agente compatible (Claude, GPT, Gemini…) sin integración a medida. La especificación MCP (rev. 2025-06-18) describe exactamente este flujo.

Caso real · robótica

El ROS MCP Server (lanzado el 11 sep 2025) expone topics, services y actions de ROS 1 y 2 como tools, permitiendo controlar robots existentes "en lenguaje natural, sin cambiar el código del robot". Es el patrón envoltorio-sobre-driver aplicado a robótica.

03 Paso 2 · El bucle agente → actuador → sensor

Controlar hardware es inherentemente cerrado: cada acción cambia el mundo físico y hay que volver a medir para decidir la siguiente.

En la práctica el modelo recibe la lectura del sensor como resultado de la tool y razona sobre ella: subió ganancia, ¿el SNR mejoró o saturó el ADC? Este ciclo es lo que distingue a un agente (itera con realimentación) de una simple llamada de función aislada. Un trabajo relacionado, el ROSBag MCP Server (nov 2025), muestra el lado de la percepción: tools que dan al LLM acceso a datos de robot (trayectorias, LiDAR) que de otro modo no cabrían en su contexto, y señala que la claridad del esquema y el número de tools correlacionan directamente con la tasa de acierto.

04 Paso 3 · HITL y HIL como salvaguarda

Antes de accionar hardware de verdad conviene interponer un humano y/o un entorno de prueba. Son dos barreras distintas y complementarias.

HITL — Human in the loop

Una persona aprueba (o deniega) la acción antes de que se ejecute. La propia especificación MCP recomienda que "siempre debería haber un humano en el lazo con capacidad de denegar invocaciones de tools", con confirmaciones visibles para operaciones sensibles.

HIL — Hardware in the loop

El comando se prueba primero contra el hardware real (o un gemelo digital/simulador) en un banco controlado, no sobre el sistema en producción. Permite validar millones de combinaciones de forma segura antes del despliegue.

La distinción importa: HITL es una barrera de autorización (¿debe esto ejecutarse?), mientras que HIL es una barrera de validación (¿funciona y es seguro en un banco antes de salir a campo?). Muchos sistemas fiables usan las dos. Un patrón común en tools es marcar las que son destructivas o irreversibles (anotaciones de la tool) para que el host exija confirmación humana explícita solo en esas.

Por qué no basta con el LLM

El análisis "LLMs Add Safety Risks to Physical AI" (6 nov 2025) documenta por qué: salida no determinista ("para el mismo prompt no obtengo exactamente la misma respuesta"), alucinaciones, y fallos por cambio de dominio. Cita un robot de ajedrez que fracturó el dedo de un niño al moverse antes de tiempo. La conclusión recurrente: la supervisión humana y los límites en tiempo de ejecución siguen siendo imprescindibles.

05 Estado, seguridad, latencia y fallos

El hardware real tiene problemas que el software puro no: el estado persiste, los comandos tardan, y las cosas se rompen a mitad de una acción.

Gestión de estado

A diferencia de una API sin estado, un actuador recuerda lo último que le pediste: el USRP sigue sintonizado, el brazo sigue en la última pose. El servidor de tools debe exponer tools de lectura (sdr_get_state) para que el agente no asuma el estado, e idealmente ser idempotente donde se pueda. "Fijar frecuencia a X" es más seguro que "subir 1 MHz", porque lo segundo depende de un estado que el modelo quizá no conoce.

Latencia y tiempo real

Un LLM razona en cientos de milisegundos o segundos; muchos lazos físicos (control de potencia RF, estabilización de un dron) exigen microsegundos. El patrón habitual es de dos niveles: el agente fija objetivos y parámetros de alto nivel ("busca la portadora en esta banda y sintonízala"), y un controlador determinista de bajo nivel —en el firmware o el driver— cierra el lazo rápido. El agente supervisa; no sustituye al control en tiempo real.

Manejo de fallos

MCP separa errores de protocolo (tool inexistente, argumentos inválidos) de errores de ejecución (isError: true en el resultado: fallo del dispositivo, timeout, límite excedido). El servidor debe validar toda entrada, aplicar control de acceso, limitar la tasa de invocaciones y poner timeouts. Un buen mensaje de error devuelve al agente qué pasó y cómo corregir, no solo "falló".

06 Cómo acotarlo para que sea fiable

La fiabilidad no sale del modelo, sale de la capa de tools que lo rodea. Estas son las defensas que se combinan.

  • Límites físicos en el esquema. Codifica rangos válidos (minimum/maximum, enums) en el JSON Schema de cada parámetro, y vuelve a validarlos en el servidor. El modelo nunca debería poder pedir una ganancia de 500 dB.
  • Validación de comandos en el servidor. No confíes en que el modelo respete el esquema: revalida todo en el envoltorio del driver, con control de acceso y rate limiting. El esquema guía; el servidor hace cumplir.
  • Dry-run / modo simulación. Ofrece una tool que calcula y devuelve lo que haría sin accionar, o apunta el agente a un simulador/gemelo digital. El RadioSim Agent (2025) es un buen ejemplo del espíritu dry-run: un agente que opera un simulador electromagnético determinista por function calling (tools como simulate_radio_environment()) en lugar de transmitir por hardware. Útil para probar el plan antes de tocar RF real.
  • Confirmación humana en acciones irreversibles. Marca como sensibles las tools que transmiten potencia, mueven masa o no se pueden deshacer, y exige aprobación HITL antes de ejecutarlas.
  • Lecturas antes y después. Haz que el agente lea el estado antes de actuar y verifique el efecto después; convierte un comando a ciegas en un lazo verificado.
  • Catálogo acotado. Expón solo las tools necesarias con descripciones nítidas: menos tools y esquemas claros elevan la tasa de acierto (hallazgo del ROSBag MCP Server).

Regla práctica

Trata al agente como a un operador capaz pero falible al que le das una consola con topes mecánicos: puede hacer su trabajo con libertad, pero la consola física le impide pedir lo imposible y un supervisor firma lo irreversible.

07 Ejemplos por dominio

El mismo patrón —driver envuelto como tools con límites, bucle cerrado y salvaguardas— se instancia en cada dominio.

SDR / radio (USRP)

Tools sobre el driver UHD: set_rx/tx (frecuencia, tasa, ganancia, antena), capture_iq, get_state. Límites de banda y potencia en el esquema; transmisión marcada como sensible (HITL), porque emitir RF tiene implicaciones legales y de interferencia.

Radar cognitivo

Investigación de 2026 explora agentes de lenguaje que condicionan la forma de onda del radar: "Small Language Model enabled Autonomous agent for Language-Conditioned Cognitive Radar" (ago 2026) apunta justo a traducir intención en lenguaje a parámetros de sensado.

Robótica (ROS 2)

El ROS MCP Server expone topics/services/actions. El agente publica objetivos de navegación o pose; controladores ROS deterministas cierran el lazo rápido.

Instrumentos de lab

Osciloscopios, generadores y fuentes vía SCPI/VISA envueltos como tools (set_voltage con tope, measure). Lectura-después-de-escritura para confirmar cada ajuste.

GPIO / PLC

Pines o relés como tools discretas con enums de estado. Los PLC ya aportan enclavamientos de seguridad; el agente opera por encima de ellos, nunca los puentea.

Manufactura

Revisiones de 2026 sobre HITL + LLM en manufactura inteligente sitúan la aprobación humana como pieza central del despliegue seguro en planta.

    Servidor MCP que expone topics, services y actions de ROS 1/2 como tools para control de robots en lenguaje natural sin modificar su código.

    Tools MCP para datos de robot; evidencia de que claridad de esquema, complejidad de parámetros y número de tools determinan la tasa de acierto del agente.
  4. RadioSim Agent: LLMs + simuladores electromagnéticos deterministas (arXiv 2511.05912) 2025
    Agente que opera un simulador de propagación por function calling. Ejemplo del espíritu "dry-run": automatizar simulación, no transmitir por hardware real.
  5. LLMs Add Safety Risks To Physical AI — Semiconductor Engineering 6 nov 2025
    Riesgos de usar LLMs para accionar hardware (no determinismo, alucinación, cambio de dominio) y salvaguardas: guardrails en runtime, gemelos digitales, co-verificación y supervisión humana.
  6. Small Language Model enabled Autonomous agent for Language-Conditioned Cognitive Radar (arXiv 2608.11596) ago 2026
    Agente de lenguaje que condiciona el sensado de un radar cognitivo; dominio directamente afín a SDR/RF. Citada por título y resumen del listado arXiv.
  7. Human-in-the-loop and LLMs in smart manufacturing — ScienceDirect 2026
    Revisión de aplicaciones, retos y perspectivas de HITL + LLM en manufactura; refuerza el papel de la aprobación humana en despliegues físicos.

Nota de honestidad

El control de hardware físico directo por agentes LLM en 2026 vive sobre todo en investigación, prototipos y entornos de simulación/HIL, no en despliegues de producción no supervisados. Donde una afirmación no tiene una fuente reciente sólida, el texto se queda en el patrón general en lugar de inventar un caso.
